# واسط Netlify برای ZVPN

مسیر اتصال: برنامه کاربر ← Netlify ← Xray فعلی سرور.

این پوشه فقط روی Netlify منتشر می‌شود؛ نصب‌کننده سرور ندارد و به سرویس‌ها، پورت‌ها یا گواهی‌های سرور دست نمی‌زند. مسیر موجود `/zvpn-xhttp/` را عبور می‌دهد؛ صفحات پنل و API مدیریت عبور داده نمی‌شوند.

## ساخت پروژه

۱. در [Netlify](https://app.netlify.com/) وارد حساب شوید و ساخت پروژه از GitHub را انتخاب کنید.

۲. مخزن `Nullfill/ZVPN` و شاخه `main` را انتخاب کنید. تنظیمات انتشار:

| گزینه | مقدار |
|---|---|
| Base directory | `deploy/netlify` |
| Build command | خالی |
| Publish directory | `public` |

۳. متغیر محیطی `TARGET_DOMAIN` را برابر دامنه HTTPS پنل خود قرار دهید؛ برای مثال `https://vpn.example.com`. این آدرس نمونه است و باید با دامنه واقعی پنل شما جایگزین شود. اگر دامنه پنل تغییر کرد، همین مقدار را به دامنه جدید تغییر دهید. مقدار باید فقط مبدأ HTTPS باشد؛ مسیر `/zvpn-xhttp/` را به آن اضافه نکنید. روی حساب رایگان از مقدار پیش‌فرض All scopes و All deploy contexts استفاده کنید. اگر حساب امکان محدوده‌گذاری دارد، Functions و محیط Production باید مشمول باشند.

۴. پروژه را منتشر کنید. پس از هر تغییر متغیر محیطی، دوباره Deploy کنید. توکن Netlify، رمز سرور یا UUID کاربران را در مخزن ثبت نکنید.

## نمایش در پنل و انتقال

پس از آماده‌شدن دامنه و HTTPS پروژه، در پنل مدیر ← تنظیمات ← واسط Netlify، دامنه واسط را وارد و نمایش کانفیگ را فعال کنید. برای تمام کاربران فعلی و جدید، کانفیگ، QR و دانلود اختصاصی خودکار نمایش داده می‌شود. لینک اشتراک Xray هر دو مسیر مستقیم و واسط را شامل می‌شود؛ لینک اشتراک Netlify فقط مسیر واسط را دارد. شناسه، حجم و انقضا مشترک است و مصرف در آمار Xray ثبت می‌شود. خاموش کردن نمایش، کانفیگ‌هایی را که قبلاً وارد برنامه شده‌اند باطل نمی‌کند.

نصب و ارتقا کد پشتیبانی را نصب می‌کنند و تنظیمات موجود را نگه می‌دارند؛ حساب یا پروژه ابری جدید نمی‌سازند. بکاپ کامل تلگرام و GitHub و میگریشن، تنظیمات و شناسه کاربران و کد واسط را نگه می‌دارند. با همان دامنه اصلی، فقط DNS دامنه اصلی به سرور جدید تغییر می‌کند و Netlify خودکار به همان دامنه روی سرور جدید وصل می‌شود؛ رکورد relay روی Netlify بماند. در صورت تغییر دامنه اصلی، TARGET_DOMAIN را در Netlify تغییر و دوباره Deploy کنید.

## آزمایش دستی کانفیگ

ابتدا فقط یک کپی از لینک Xray فعلی یک کاربر را آزمایش کنید. برای این واسط تغییر نام دامنه به‌تنهایی کافی نیست: کانفیگ کلاینت باید padding سازگار Netlify را هم داشته باشد. لینک فعلی کاربر را در یک فایل خصوصی ذخیره کنید و با ابزار زیر لینک آزمایشی بسازید:

```text
node make-link.mjs INPUT_FILE PROJECT.netlify.app OUTPUT_FILE
```

UUID همان کاربر، پورت ۴۴۳، مسیر `/zvpn-xhttp/` و حالت `packet-up` باقی می‌مانند. این ابزار فقط نسخه آزمایشی را می‌سازد؛ فایل فعلی کاربر را تغییر نمی‌دهد و UUID را در خروجی ترمینال چاپ نمی‌کند. فایل ورودی و خروجی حاوی اطلاعات اتصال خصوصی‌اند و نباید داخل GitHub یا فایل‌های عمومی Netlify قرار بگیرند.

برای دامنه اختصاصی که در همین پروژه Netlify ثبت شده و DNS و گواهی معتبرش آماده است، نام آن را به‌جای `PROJECT.netlify.app` قرار دهید و گزینه `--custom-domain` را به انتهای دستور اضافه کنید. گواهی باید برای همان نام معتبر باشد؛ اعتبارسنجی TLS را خاموش نکنید.

ممکن است IP پیش‌فرض Netlify از یک اینترنت در دسترس نباشد ولی ورودی منطقه‌ای دیگری از همان سرویس قابل اتصال باشد. IP جایگزین باید از پاسخ DNS خود Netlify به دست بیاید و با نام دامنه پروژه، گواهی معتبر و انتقال واقعی داده آزمایش شود. صرف بازبودن پورت کافی نیست. IPهای منطقه‌ای ممکن است در آینده تغییر کنند؛ رکورد دامنه واسط محل تغییر مسیر است و کانفیگ کاربران می‌تواند همان نام دامنه را نگه دارد.

در تست واقعی، Netlify به قالب قدیمی padding در Referer پاسخ ۴۲۹ داد. واسط، هدر `X-Relay-Padding` کلاینت آزمایشی را به قالب فعلی سرور تبدیل می‌کند؛ پاسخ سرور نیز برای همین کلاینت ترجمه می‌شود. تنظیم Xray و کانفیگ‌های مستقیم فعلی عوض نمی‌شوند. انتقال واقعی داده از این مسیر و ثبت مصرف در حساب فعلی آزمایش شده است؛ پایداری و اتصال از اینترنت هر کاربر باید جداگانه بررسی شوند. بازشدن صفحه اصلی Netlify یا دریافت پاسخ HTTP به‌تنهایی به معنی کارکرد VPN نیست.

اتصال از اینترنت مودم را جداگانه بررسی کنید؛ کارکرد از داخل VPN یا از خود سرور، اتصال مستقیم مودم به Netlify را ثابت نمی‌کند. این واسط کشور خروجی اینترنت را عوض نمی‌کند؛ خروجی همچنان سرور یا WARP انتخابی آن است. حساب و مصرف کاربر فقط در صورت استفاده از همان UUID و Xray فعلی، در مسیر حسابداری فعلی پنل قرار می‌گیرد.

در مهاجرت سرور، رکورد دامنه واسط باید روی Netlify بماند؛ آن را به IP سرور VPN جدید تغییر ندهید. فقط رکورد دامنه مبدأ پنل به سرور جدید منتقل می‌شود. اگر نام دامنه مبدأ ثابت بماند، `TARGET_DOMAIN` تغییر نمی‌کند. پروژه‌ای که با CLI به‌صورت دستی منتشر شده، خودکار با هر تغییر GitHub منتشر نمی‌شود؛ برای تغییر کد واسط باید مجدداً Deploy کنید یا انتشار از GitHub را جداگانه تنظیم کنید.

Netlify برای اجرای Edge Functions و تعداد درخواست‌ها محدودیت دارد. سقف انتظار برای هدر پاسخ ۴۰ ثانیه است؛ تعداد فراخوانی مجاز به طرح حساب بستگی دارد. پایداری و هزینه استفاده عمومی باید پیش از انتشار برای همه کاربران ارزیابی شود.

## اشتراک مشترک کاربران

صفحه اختصاصی هر کاربر یک لینک و QR اشتراک دارد که مسیر مستقیم و Netlify را یکجا وارد برنامه می‌کند. یک ردیف با عنوان «اطلاعات اشتراک» حجم باقی‌مانده و روزهای اعتبار را نشان می‌دهد؛ این ردیف برای اتصال نیست. اطلاعات با بروزرسانی اشتراک تازه می‌شوند. برنامه‌های سازگار، مصرف و انقضا را از اطلاعات استاندارد ساب هم می‌خوانند. لینک‌های اشتراک قدیمی همچنان کار می‌کنند.

## تفکیک مصرف Netlify از نسخه ۳.۲

نسخه جدید واسط، مسیر عمومی قبلی را به ورودی اختصاصی Netlify روی سرور می‌فرستد. حساب و سهمیه همان حساب قبلی است، ولی مصرف هر مسیر جدا ثبت می‌شود. هنگام ارتقا از نسخه قدیمی، اول سرور را آپدیت کنید، سپس آخرین پوشه deploy/netlify را در همان پروژه Netlify دوباره منتشر کنید؛ اگر پروژه به GitHub متصل است، انتشار خودکار پس از آپدیت سرور انجام شود. کانفیگ مشتری عوض نمی‌شود. برای میگریشن‌های بعدی با همین دامنه، انتشار مجدد لازم نیست.

در پنل، مصرف پیش از تفکیک جدا نمایش داده می‌شود؛ آن را نمی‌توان با اطمینان به مستقیم یا Netlify نسبت داد.
